## 1. Цель

Закрыть последние три критерия «Первого контрольного результата» (BRIEF_v2 §15):
- **6.** Создание плейлиста.
- **7.** Сохранение любимой композиции.
- **8.** Синхронизация аккаунта с backend: изменение на одном клиенте видно на втором без перезагрузки; изменения, сделанные без сети, доходят после её появления.

После I7 остаётся I8 (стабилизация → v0.1.0).

## 2. Разбиение

| Часть | Результат | Оценка |
|---|---|---|
| **I7a — библиотека и плейлисты** | REST API лайков треков, сохранённых альбомов, подписок на исполнителей, плейлистов, журнала изменений; экраны «Библиотека» (треки, плейлисты, альбомы, исполнители), плейлист; сердечко и «Добавить в плейлист» в списках и плеере, «Сохранить» у релиза, «Подписаться» у исполнителя. Работает онлайн, второй клиент видит изменения при открытии страницы или возврате на вкладку | 3,5 дня |
| **I7b — синхронизация в реальном времени и офлайн** | WebSocket-уведомления, `/sync/changes`, пакет `@mp/sync` (очередь изменений, повторы, идемпотентность), хранилище в IndexedDB, история прослушиваний, перенос настроек воспроизведения на сервер, E2E «два клиента» | 2–3 дня |

I7a можно проверить и закоммитить отдельно: это уже критерии 6 и 7, а WS и офлайн из I7b добавляют критерий 8.

## 3. Вне рамок I7 (честно)

- Синхронизация воспроизведения (текущий трек, очередь, позиция между устройствами) и Handoff — Phase 3, вместе с мобильным клиентом. Сейчас очередь и позиция хранятся только локально (I6b).
- Публичные и совместные плейлисты, ссылки «поделиться» — Phase 6 (ADR-011: CRDT рассмотреть там).
- Импорт плейлистов из других сервисов, личные загрузки — Phase 4.
- Обложки плейлистов из картинок: у каталога нет обложек, поэтому обложка плейлиста генерируется так же, как у релизов (из id), или мозаика из обложек его треков.

## 4. Модель данных (миграция после `0004` — статус прав, ADR-023)

```
users.change_seq bigint not null default 0          — счётчик версий библиотеки пользователя

user_change_log (user_id, seq)  PK                    — журнал изменений, основа синхронизации
  entity  text   (track_like | release_save | artist_follow | playlist | playlist_item | settings)
  entity_id uuid, op text (upsert | delete), payload jsonb, mutation_id uuid null, created_at

library_tracks   (user_id, track_id) PK, liked_at     — «Любимые треки»
library_releases (user_id, release_id) PK, saved_at   — сохранённые альбомы
library_artists  (user_id, artist_id) PK, followed_at — подписки на исполнителей

playlists      id uuid PK, owner_id, name (1–100), description (≤ 300), created_at, updated_at, deleted_at
playlist_items id uuid PK, playlist_id, track_id, position text (дробный ключ), added_at
               unique (playlist_id, position); индекс (playlist_id, position)

play_events    id uuid PK, user_id, track_id, started_at, played_ms, completed, skipped,
               session_id (устройство), context_type/context_id (release | artist | playlist | library | search),
               client_event_id uuid — unique (user_id, client_event_id), повтор не создаёт дубль

user_settings  user_id PK, playback jsonb (zod-схема из @mp/contracts),
               history_enabled boolean not null default true, updated_at

idempotency_keys (user_id, key) PK, status int, response jsonb, created_at — хранится 24 ч
```

Правила:
- **Каждая мутация — одна транзакция:** `UPDATE users SET change_seq = change_seq + 1 RETURNING` (блокировка строки пользователя упорядочивает его изменения) → изменение данных → запись в `user_change_log` → запись ключа идемпотентности. После коммита — `PUBLISH user:<id>` в Redis.
- Лайки и сохранения идемпотентны сами по себе (PUT/DELETE): повтор ничего не меняет и не создаёт новую версию.
- Позиции в плейлисте — **дробные строковые ключи** (fractional indexing): «вставить между A и B» не трогает другие строки, одновременные вставки с двух устройств не конфликтуют. При равенстве ключей добавляется суффикс из id элемента.
- Удалённый плейлист — tombstone (`deleted_at`), чтобы офлайн-клиент получил `delete`, а не «пропажу». Физическая очистка — через 90 дней.
- Трек, который пропал из каталога (истекло право), **остаётся** в плейлисте и в «Любимых» с меткой «Недоступно» и без кнопки «Играть». Это правило видимости ADR-018 для списков пользователя.
- Журнал хранится 90 дней. Клиент, который отстал сильнее, получает `410 Gone` и делает полную перезагрузку библиотеки.
- Лимиты: 10 000 треков в плейлисте, 1 000 плейлистов, 100 000 лайков (ошибка RFC 9457 с понятным текстом).
- **Дубли в плейлисте разрешены** (решение заказчика): уникальность только по `(playlist_id, position)`. Если добавляемый трек уже есть, `POST /playlists/:id/items` отвечает `409 duplicate_tracks` со списком; клиент показывает «Уже в плейлисте — добавить ещё раз?» и повторяет запрос с `allowDuplicates: true`. Предупреждение — на сервере, поэтому одинаково на всех клиентах.
- **Режим «Не записывать историю»** (`history_enabled = false`): клиент не отправляет отчёты, а сервер их игнорирует (`202`, `recorded: 0`) — на случай старого клиента или офлайн-очереди, отправленной после выключения. Уже записанное не удаляется (для этого «Очистить»). Переключатель — в аккаунте, состояние синхронизируется.
- «Прослушивание» в истории — от 30 с или половины трека (что меньше). Пропуск раньше — `skipped`.

## 5. API

Все эндпоинты — только после входа. Мутации принимают заголовок `Idempotency-Key` (uuid): повтор с тем же ключом возвращает сохранённый ответ; тот же ключ для другого запроса — 409. Каждый ответ мутации содержит `seq`. Ошибки: `DUPLICATE_TRACKS` (409, в `errors` — `trackIds.<i>`), `LIMIT_EXCEEDED` (409).

> Реализация I7a (05.11): сделаны библиотека, плейлисты, журнал изменений и ключи идемпотентности. История, настройки, `/sync/*`, WebSocket — I7b, таблицы `play_events` и `user_settings` появятся отдельной миграцией вместе с ними.

| Метод и путь | Назначение |
|---|---|
| `GET /library/tracks?cursor=` | «Любимые треки», новые первыми, курсорная пагинация |
| `PUT /library/tracks/:id`, `DELETE /library/tracks/:id` | лайк / снять лайк (идемпотентно) |
| `GET /library/releases`, `PUT/DELETE /library/releases/:id` | сохранённые альбомы |
| `GET /library/artists`, `PUT/DELETE /library/artists/:id` | подписки на исполнителей |
| `POST /library/contains` `{ tracks?, releases?, artists? }` (≤ 100 каждого) | состояние сердечек / «Сохранено» / «Подписка» для экрана одним запросом |
| `GET /playlists` | мои плейлисты (название, число треков, длительность, обновлён) |
| `POST /playlists` `{ name, description? }` | создать |
| `GET /playlists/:id` | плейлист: название, описание, число треков, длительность |
| `GET /playlists/:id/items?cursor=&limit=` | треки по порядку страницами (до 500; ТЗ v3 §15.4 — пагинация больших коллекций), у каждого `itemId`, доступность, лицензия |
| `PATCH /playlists/:id`, `DELETE /playlists/:id` | переименовать / описание / удалить. Чужой плейлист → 404 |
| `PUT/DELETE /library/…` | ответ `{ seq }` с кодом 200 (а не 204), чтобы клиент знал версию библиотеки |
| `POST /playlists/:id/items` `{ trackIds, after?: itemId \| null, allowDuplicates?: boolean }` | добавить один или несколько треков (по умолчанию в конец); уже имеющиеся без `allowDuplicates` → 409 со списком |
| `PATCH /playlists/:id/items/:itemId` `{ after: itemId \| null }` | переместить |
| `DELETE /playlists/:id/items/:itemId` | убрать трек |
| `POST /history/plays` `{ events: [...] }` (≤ 50) | отчёты о прослушивании пачкой |
| `GET /history/recent` | недавно прослушанные треки (без повторов подряд) |
| `DELETE /history` | очистить историю (приватность) |
| `GET /me/settings`, `PUT /me/settings` | настройки воспроизведения (сейчас `remusic.player.settings.v1` в localStorage) и `historyEnabled` |
| `GET /sync/changes?since=&limit=500` | изменения после версии: `{ changes, seq, hasMore }`; слишком старая версия → 410 |
| `POST /sync/ws-ticket` | одноразовый билет на 30 с для WebSocket |
| `WS /ws?ticket=` | канал уведомлений (I7b) |

Контракты — zod-схемы в `@mp/contracts` (`library.ts`, `playlists.ts`, `history.ts`, `sync.ts`), методы — в `@mp/api-client`, OpenAPI генерируется как раньше.

**WebSocket — только уведомление, не данные.** Сервер шлёт `{ type: "changed", seq }`, клиент забирает изменения через `GET /sync/changes`. Так один путь данных (REST, с правами, валидацией и тестами), WS можно потерять без последствий, и это одинаково работает для web, Windows и мобильных. Реализация — `@nestjs/websockets` + `ws` (не socket.io: проще для нативных клиентов), Redis pub/sub между инстансами API, ping каждые 25 с, закрытие при выходе из аккаунта и отзыве сессии.

**Почему билет, а не токен в URL:** access-токен веба хранится в памяти и в URL попадать не должен (логи, история). Билет одноразовый, живёт 30 с и привязан к сессии.

## 6. Клиент

### `@mp/sync` (новый пакет, чистый TS, без DOM)
- `SyncEngine`: очередь исходящих мутаций (outbox) с `mutationId`/`Idempotency-Key`, оптимистичное применение, отправка по порядку, повторы с экспоненциальной задержкой при сетевых ошибках и 5xx, откат и сообщение при 4xx.
- Хранит курсор `seq`, принимает изменения сервера и пропускает те, что сам же отправил (по `mutationId`).
- Порты: `Transport` (api-client), `Storage` (IndexedDB в вебе, SQLite в мобильных в Phase 3), `Clock`, `Notifier` (WS). Всё покрывается unit-тестами на фейках.
- Догоняет при старте, при восстановлении сети, при возврате на вкладку и раз в 60 с, если WS недоступен.

### Веб (`apps/web`)
- **Библиотека** `/library`: вкладки «Любимые треки», «Плейлисты», «Альбомы», «Исполнители», «Недавние»; пустые состояния с действием («Найдите трек и нажмите ♥»), а не пустые страницы.
- **Плейлист** `/playlist/[id]`: «Слушать» и «Вперемешку», переименование, описание, удаление с подтверждением, удаление трека с «Отменить», перестановка перетаскиванием **и с клавиатуры** (доступность), метка «Недоступно».
- **Сердечко** в строках треков (релиз, исполнитель, поиск, плейлист), в нижнем и полноэкранном плеере. Горячая клавиша `L`.
- **«Добавить в плейлист»** — меню у трека и в плеере: список плейлистов, «Новый плейлист», предупреждение, если трек уже есть.
- **Боковая панель** (реф. 1): «Библиотека», «Любимые», список плейлистов, «Недавние». На телефоне — пункт «Библиотека» в нижней навигации.
- Плеер отправляет отчёты о прослушивании (через outbox, переживают офлайн) и передаёт контекст (релиз, плейлист…).
- Индикатор «Нет сети — изменения отправятся позже» и счётчик неотправленных.
- ru/en, обе темы, мобильная вёрстка 390 px — как в прошлых итерациях.

## 7. Тесты

- **Integration (API, реальные Postgres/Redis):** идемпотентность (тот же ключ дважды → одно изменение, тот же ответ); `seq` строго растёт без пропусков при 20 параллельных мутациях одного пользователя; `/sync/changes` с пагинацией и 410; все операции плейлиста, включая вставку между элементами и одновременные вставки; чужой плейлист → 404; лимиты; недоступный трек остаётся в списке; история без дублей по `client_event_id`; WS: два подключения одного пользователя получают `changed`, чужое — нет; отзыв сессии закрывает сокет.
- **Unit:** `@mp/sync` (outbox, повторы, откат, пропуск своих изменений, догоняние), дробные ключи (свойства: порядок сохраняется на 10 000 случайных вставок), правило «прослушивания».
- **E2E (Playwright, первые E2E проекта):** два браузерных контекста одного пользователя — лайк в A виден в B ≤ 2 с; плейлист создан в A при `setOffline(true)` → сеть вернулась → плейлист в B; перестановка в A → тот же порядок в B.
- **`setup.bat`:** новый шаг `sync:smoke` — два API-клиента на dev-базе: лайк, плейлист, перестановка, догоняние через `/sync/changes`.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Прокси Next.js (`/api/*`) может не пропускать WebSocket в dev и prod | Первый шаг I7b — короткий спайк. Запасной вариант: WS напрямую на порт API с проверкой `Origin` + билет (cookie не нужна) |
| IndexedDB недоступна (приватный режим старых браузеров) | Outbox в памяти + предупреждение «изменения без сети не сохранятся» |
| Рост `play_events` | Индекс (user_id, started_at desc); партиционирование по месяцам — когда станет нужно (Phase 5) |
| Много вкладок одного пользователя шлют одно и то же | Идемпотентность на сервере; outbox одной вкладки через Web Locks API |

## 10. Решения заказчика (05.11)

1. **Альбомы и исполнители — в I7:** сохранение альбомов и подписка на исполнителей входят в I7a (+0,5 дня).
2. **Дубли в плейлисте — разрешены с предупреждением** (§4, §5: `409 duplicate_tracks` → «добавить ещё раз?»).
3. **История — включена по умолчанию, есть «Очистить» и режим «Не записывать историю»** (§4).
4. **Синхронизация очереди и позиции между устройствами** переносится из I7 (как было записано в ADR-019) в Phase 3 вместе с Handoff — см. §3 и ADR-020.
